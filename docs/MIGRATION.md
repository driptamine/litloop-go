# Перенос и отличия

`source-models.json` фиксирует 92 определения моделей из исходных приложений; дополнительно перенесены три неявные many-to-many таблицы. В Go модели размещены в 24 пакетах в корне проекта. `source-routes.json` фиксирует 237 объявлений URL из подключённых приложений и главного URLConf, включая повторяющиеся aliases. Папка `y_tinkering/` не читалась при построении этих реестров и не переносилась.

Публичные URL сохранены. Добавлены `/healthz`, `/readyz`, `/openapi.json`, `/notifications`, `/jobs/api/companies`, `/jobs/api/resumes`, `/videos/<id>/encode`, `/tasks/<id>`, служебные URL загрузки и выдачи медиа. `openapi.json` является реестром маршрутов с общей схемой тела, а не полной типизированной спецификацией каждого ответа.

## База данных

SQL-имена таблиц и колонок сохранены (`users_user`, `posts_post`, и т.д.), как и nullable foreign keys, timestamps, through-таблицы и связи удаления. Новые служебные таблицы имеют префикс `go_`. Регистрация миграций находится в `internal/models/registry.go`.

Рекомендуемый переход: восстановить копию PostgreSQL в отдельную БД, указать её `DATABASE_URL`, выполнить `cmd/migrate`, сверить данные и клиентские сценарии, затем переключать трафик. Сама разработка не подключалась к исходной рабочей БД и не переносила пользовательские данные. Если в текущей схеме PostgreSQL есть таблица `django_migrations`, мигратор добавляет отсутствующие таблицы и колонки в одной транзакции. Совместимость данных и клиентских сценариев проверяется на копии. Cassandra-эксперименты и прежние варианты шардирования заменены основной SQL-моделью.

Пароли `pbkdf2_sha256`, `bcrypt` и `bcrypt_sha256` проверяются при входе; новые пароли хешируются bcrypt. Для старых JWT можно установить тот же `SECRET_KEY` через `JWT_SECRET`. Старые access-токены без `token_type` принимаются до срока действия, старые refresh-токены нужно переиздать новым входом. Django session cookies и Django password-reset tokens не переносятся. Деревья обходятся через `parent_id`; при записи и удалении пересчитываются MPTT-индексы `lft`, `rght`, `tree_id`, `level`. На PostgreSQL пересчёт сериализуется транзакционной блокировкой.

## Изменённое поведение

- Авторизация и владение проверяются для приватных ресурсов. Убраны обходы с подстановкой пользователя `alice` и тестовыми пользовательскими ID.
- Ссылки доступны текущему пользователю. Медиа для прикрепления к посту должны принадлежать автору. Приватное видео доступно владельцу либо после публикации через пост.
- `/maintenance/*` требует POST и superuser. Операции delete очищают соответствующие записи с каскадами, а regenerate применяет миграции; это замена прежних GET-обработчиков drop/recreate tables. `/admin` — JSON API вместо Django Admin UI.
- Статистика записывается транзакционно в SQL вместо Redis-счётчиков с периодическим Celery flush. Фоновая очередь хранится в `go_tasks`; Celery и RabbitMQ не нужны. WebSocket-рассылка использует Redis только при заданном `REDIS_URL`.
- JSON-ответы нормализованы: в каталоге сохранены URI-идентификаторы и отдельный `pk`; многие списки используют `total`, `num_pages`, `current_page`, `items`. Не все старые нестабильные envelopes и провайдерские ответы совпадают с Django. Проверка URL не заменяет проверку контракта фронтенда.
- Устранены обращения к отсутствующим полям `Playlist.name`, `Application.user`, `Application.cover_letter`, `JobPosting.created_at`. Используются действительные поля `title`, `applicant_id`, отдельный CoverLetter, `posted_at`.
- Multipart-upload привязан к пользователю, сессии и сгенерированному ключу; переданный клиентом ключ не может переключить чужую сессию. Пароли новых аккаунтов должны занимать 8–72 байта. Сброс пароля отправляет письмо через SMTP вместо возврата reset-link в публичном ответе.
- Фото профиля и сообществ используют постоянные capability URL `/assets/<случайный-id>`; доступ к остальному локальному медиа выдаётся подписанными URL на час. Локальные multipart-вложения ограничены 64 MiB, PUT-загрузка — 512 MiB, скачивание worker — 2 GiB. Облачная загрузка выполняется напрямую в хранилище.
- Видео обрабатывается FFmpeg в HLS с H.264/AAC и thumbnail. Автоматический запуск Spot VM вынесен в настраиваемый HTTP-адаптер `SPOT_LAUNCH_URL`; специфичные GCP shell-скрипты и приватная инфраструктура не выполняются. API не содержит ключей из исходника.
- `broadcasts` и `magazines` не подключены в исходном главном URLConf. Их модели перенесены и доступны через административный API; несуществующая checkout-интеграция не добавлена.

## Внешние зависимости

Каждый провайдер использует свои параметры из `.env.example`. Без нужных настроек интеграционные endpoints возвращают 503. Google OAuth использует authorization-code exchange или проверку `id_token` и audience; VK — authorization-code exchange. Redirect URI Google: `FRONTEND_URL/auth/google/callback`.

S3/R2/GCS HMAC требуют соответствующих credentials. Native GCS требует JSON service account по `GOOGLE_APPLICATION_CREDENTIALS`; этот файл нужно отдельно примонтировать в контейнеры. Сервер выдаёт private native GCS объекты через подписанный proxy URL. Если worker работает на другой машине, нужен общий каталог медиа или отдельный этап выгрузки результатов HLS во внешнее хранилище.

HTTP-адаптеры внешних API проверяются на подставных ответах. Реальные OAuth, облачные бакеты, SMTP, GCP Spot и транскриптор требуют проверки с пользовательскими ключами. Проверки выполняются на SQLite и локальном PostgreSQL 17.9; межсерверная WebSocket-рассылка — на Redis 7.4.2, преобразование MP4 в HLS и выдача сегментов — на FFmpeg 6.1.1. Для повторного запуска задайте `TEST_DATABASE_URL`, `TEST_REDIS_URL` и добавьте `ffmpeg` в `PATH`. Docker в текущем окружении отсутствует; compose-сценарий запускается отдельно.
